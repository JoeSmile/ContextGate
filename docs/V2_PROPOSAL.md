> 状态:待拍板 · 2026-08-02 · 作者:Hermes

> 关联:`docs/COMPETITIVE_ANALYSIS.md`(治理层定位)、`docs/ROADMAP.md`(v2.0 段待更新)。

## 0. 一句话战略

**治理层做透 + 垂直场景做深,不横铺功能。**

v1.x 已经把"治理层"的地基立住了(认证/护栏/审计/成本/路由/观测/加密 Key 七件套)。
v2.0 不是继续加第七、第八个横切功能,而是把现有能力从**"有"**变成**"能交付"**:

- 有审计 → 能一键出合规报表(客户验收要的)
- 有护栏 → 客户能自己调规则(不调 = 只能我们改代码)
- 有成本统计 → 能管预算、能告警(CIO 问"花了多少钱"要答得上来)
- 有本地模型能力 → 有"数据不出域"的合规背书(国企红线)
- 有八项能力 → 有一个场景把它串成 95 分(样板间)

## 2. 方向详解

### 2.1 合规交付物自动化(审计报表一键生成)

**企业问题:** 国企采购 AI 平台,验收硬项是"每一次 AI 调用可审计、可溯源、可导出"。
现在合规部门拿到的是 CSV 原始日志,要自己筛租户/时间窗/风险等级、自己排版,一单半天。
等保 2.0 三级、数据安全法、PIPL 的合规材料里,"审计报表"是直接引用的交付物。

**现状(已核实):**
- `audit_logs` 全量落库,含 trace_id / key 版本 / token / 成本 —— 数据齐
- `backend/routers/audit.py` `/api/audit/export` 已有 CSV 导出(`audit:export` 权限)

**差距:**
1. 只有 CSV,无 Excel / PDF 模板
2. 无预置报表维度(按租户 / 时间窗 / 风险等级 / 模型成本汇总)
3. 无"导出留痕"——谁导了审计数据,本身没进审计
4. 无合规打包概念(报表 + 原始日志 + 护栏配置快照 = 完整证据链)

**方案 A(精简):** 导出扩展 —— Excel 模板(openpyxl)+ 预置筛选参数,复用现有查询。
**方案 B(完整):** 合规报表子系统 —— 报表模板库 + 定时生成 + 导出留痕 + 配置快照打包。

**推荐:先 A 打底 + 加"导出留痕"一个点,PDF 后置。**
依据:① Excel 是国企合规实际交换的格式,PDF 是锦上添花;② 导出留痕是安全审计 P1 级要求(审计数据本身要审计),成本极低;③ B 的定时生成/打包,等有真实客户反馈再上,避免过度设计。

**验证:** 导出留痕写入 audit_logs;Excel 模板字段与 CSV 一致;权限 gate 不破。
**不做:** BI 大屏、报表自定义 SQL、定时邮件推送。

### 2.2 护栏规则可配置化

**企业问题:** 护栏规则现在是死的:注入模式、PII 类型、输出敏感词全硬编码。
金融客户要更多 PII 类型(银行卡/征信),军工要自定义敏感词,同一集团不同子公司规则不同。
硬编码 = 客户每次调规则都要我们发版 = 企业采购一票否决。

**现状(已核实):** `backend/core/guardrails/` 四文件(injection_patterns / pii_patterns / input_guard / output_guard),
规则为 Python 常量,`guardrails_input` / `guardrails_output` 节点在管线中消费。

**差距:**
1. 规则不在 DB,运行时不可调
2. 无管理端 UI,无租户级覆盖(全局 vs 租户)
3. 规则变更无版本、无审计(护栏规则本身也要留痕)

**方案 A(配置驱动):** 规则搬 DB + `/api/guardrails` 管理端点 + 代码默认值兜底,先不做 UI。
**方案 B(A + UI):** admin.html 加"护栏规则"Tab + 规则版本快照(每次生效变更入 audit)。

**推荐:A 先行,UI 放窗口 2 后半。**
依据:① 规则引擎重构动的是核心安全路径,必须先以最小面验证语义(租户覆盖优先级、非法规则拒绝),UI 不改变语义;② 默认安全不能降——配置只能"同级或更严",这条写进验收。

**风险(重点):** 护栏是安全防线,配置化不能变成"把规则调松"的入口。
**验证:** 默认规则行为与现版本完全一致(回归测试);租户覆盖生效;非法规则被拒;变更留痕。
**不做:** 正则在线调试器、规则市场、AI 自动生成规则。

### 2.3 租户预算与配额策略

**企业问题:** CIO 的原话场景:"这个月 AI 花了多少钱、哪个部门超了、怎么拦住"。
现在只能**看**(cost_summary),不能**管**。月度预算 + 软限告警 + 硬限熔断,是"从能看到能管"的临门一脚。
ROADMAP 已列"Tenant budget / 配额策略(硬限·软限)",本提案把它具体化。

**现状(已核实):**
- `backend/core/cost_manager.py` `check_budget()` —— 只查全局 `budget.daily_limit`(config 硬编码,默认 10.0)
- `cost_summary()` + `backend/routers/admin.py` `/api/admin/cost-summary` —— 只聚合,不设限

**差距:**
1. 限额是全局 config,不是租户级 → 新表 `tenant_budgets`(tenant_id / 周期 / 软限 / 硬限)
2. 无软限告警(80% 提醒)、无硬限熔断(超限拒绝或降级)
3. 无告警通道(webhook / 邮件)
4. 成本看板无预算进度

**方案 A:** 租户预算表 + 软/硬限检查(check_budget 扩展)+ 看板进度条。
**方案 B:** A + 告警通道(webhook)+ 超限自动降级(硬限后自动切同 tier 便宜模型)。

**推荐:B,分两步落:先 A(表 + 软硬限 + 看板),告警和降级放窗口 1 后半。**
依据:① 超限自动降级是"省钱"卖点,且 ModelRegistry 策略路由已就位(cheapest-in-tier 已有),联动成本可控;② 先 A 能最快给 CIO 一个可演示的"预算管理"页面。

**验证:** 预算表 CRUD;软限触发告警记录;硬限拒绝(403 结构化错误码);看板进度正确。
**不做:** 部门级分摊/成本中心(超卖)、充值计费、发票。

### 2.4 敏感数据不出域(本地模型 + 合规背书)

**企业问题:** 数据出境是国企红线(数据安全法)。云上 API 模型天然不满足
"敏感数据不出内网"。这也是国产化替代采购的硬条件之一。

**现状(已核实):**
- `backend/core/model_registry.py` 支持任意 OpenAI 兼容端点 → 本地 vLLM 可注册(Windows 32G/4070S 已规划)
- 多模态(whisper / PaddleOCR)v1.2 已落地

**差距:**
1. "不出域"只有能力,没有背书材料(部署文档 / 合规章节)
2. 无"本地优先"强制路由(敏感请求 → 本地模型,可配置)
3. 无数据出境检测(请求含 PII/敏感标签 → 拦截或强制本地路由)

**方案 A:** 文档背书 + 部署模板(本地 vLLM + ContextGate 一键部署脚本 + 等保/密评材料引用段落)。
**方案 B:** A + 路由策略扩展(请求敏感度标签 → 强制本地模型路由)+ 出境检测。

**推荐:先 A + 路由策略,出境检测后置。**
依据:① 背书材料零代码成本,立刻可放进售前;② 强制路由是"策略"不是"检测",不引入误判风险;③ 诚实红线:本地 7B 模型质量 vs 云上大模型的差距必须写清楚,不是所有场景都适合本地。

**前置条件:** Windows 迁移 + vLLM 真机验证(macOS 无法验收)。
**验证:** 本地端点注册 → 强制路由生效 → LangFuse trace 显示 provider=local。
**不做:** 模型蒸馏/微调(另一个项目)、硬件推荐营销。

### 2.5 垂直场景样板:国企制度问答助手

**企业问题:** 国企采购看的不是功能清单,是"能不能解决我这个问题"。
制度问答(制度库 RAG + 意图识别 + 审批 + 审计 + 本地模型)是国企 AI 最高频场景。
八项能力各 80 分,不如一个场景 95 分——样板间就是给 CIO 看的 95 分。

**现状(已核实):** examples/ 已有 7 个测试页(rag / intent / admin / streaming 等);
seed_pgvector 已含企业场景种子;管线双路径 / A/B / 成本全就位。

**差距:**
1. 没有一个"制度库 → 问答 → 审批 → 审计报表"贯通样板
2. 无场景 SOP(数据准备 → 上线 → 合规交付)
3. 无基准评测(检索命中率 / 回答准确率,可复现脚本)

**方案 A:** 场景样板(制度库 seed + 专用示例页 + SOP 文档),复用现有能力,几乎零新增核心代码。
**方案 B:** A + 场景评测(评测集 + 指标脚本,可复现)。

**推荐:A 必做;B 视证据包结果。**
依据:① 这是 ai-platform 迁移的经验载体,也是技术长文营销素材;② 样板必须走配置化/plugin 路径,
不硬编码"制度问答"概念(用户既定原则:通用工具不做业务硬编码)。

**验证:** 全链路 curl 走通(seed → RAG → 审批 → 审计查询)+ 评测指标可复现。
**不做:** 行业专用前端、多场景铺开、行业知识包售卖。

### 2.6 ai-platform integration

ROADMAP 已列。方向:ContextGate 作为 ai-platform 的治理网关层(Dify/Coze/NocoBase
可注册为 ModelRegistry provider 的互操作验证,见 COMPETITIVE_ANALYSIS §3.5)。
**建议:** 窗口 2 末期再细化为具体任务(API 形态 / 鉴权对接 / 部署拓扑),
现在写太虚,容易变成"两个项目互相 import"的烂账。

### 2.7 Multi-region deployment

**建议降级。** 多 region 是云厂商场景;国企交付是私有化单域,开源 star 也用不上。
把"多 region 功能"从 v2.0 移除,替换为"运维文档完善 + 高可用方案(备份/恢复演练)",进文档待办。

## 4. 与竞品/护城河的关系

| 方向 | 竞品对照 | 结论 |
|------|----------|------|
| 2.1 合规报表 | Dify 企业版有类似但绑定平台;LiteLLM 只有 API 级统计 | 我们已有全字段审计,做报表是"最后一公里" |
